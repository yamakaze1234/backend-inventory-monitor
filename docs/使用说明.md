# 使用说明

本说明对应当前通用版源码。正式版本和实际验收范围以 [Gitea 发行说明](https://gitea.cq360.top/CoreStudio/backend-inventory-monitor/releases) 为准。

## 适用范围

程序用于 Windows x64 桌面环境，当前项目的实际验收环境为 Windows 11。Windows 10 需要部署方验证完整业务流程；不提供 Win7、32 位、macOS 或 Linux 安装包。

“通用”表示各部门使用自己的工作区、店铺、ERP 连接和通知对象。SQL 适配器仍面向下表结构；不同 ERP 或字段名称需要修改适配器。订单匹配依赖独立匹配工程，发行包内的兼容层不包含完整匹配系统。

## 一键部署环境

源码开发使用 `tools/一键部署环境.cmd -Mode Development`，由 uv 按锁文件准备 Python 与开发依赖；普通运行模式不安装 uv 或开发依赖。源码模式需包含 `pyproject.toml`、`uv.lock` 和 `.python-version`。

将发行包完整解压，双击包根目录的 `一键部署环境.cmd`（源码目录入口位于 `tools`）。默认检查并补齐 PowerShell 7 和 WebView2，已有组件会先检测。此脚本用于环境准备，不填写业务账号、不启动订单匹配或发送消息。

需要抖店浏览器功能时，在包根目录的终端运行：

```powershell
./一键部署环境.cmd -IncludeBrowser
```

只检测、不安装：

```powershell
./一键部署环境.cmd -CheckOnly
```

部署脚本通过 Windows 包管理器安装缺失组件，网络不可用、缺少包管理器或系统安装权限时按错误提示处理，再运行检测。安装器可能需要用户确认。引导入口优先使用 PowerShell 7；新电脑尚未安装时临时使用系统自带 Windows PowerShell 5.1 启动部署流程。

| 场景 | 环境 |
| --- | --- |
| 运行已打包程序 | WebView2；内置 Python、数据库查询驱动及 DWS |
| 程序内更新 | PowerShell 7 和可访问发行源的网络 |
| 抖店巡检 | Chrome、Node.js、本人有权限的店铺登录与维护表；用 `-IncludeBrowser` 准备组件 |
| ERP SQL 查询 | 可访问管理员提供的数据库地址，具备相应对象读取权限 |
| 钉钉通知和监听 | 按所用通知类型配置机器人及账号，首次登录由使用者完成 |
| 源码开发 | `-Mode Development`，详见 [开发与构建](开发与构建.md) |

浏览器扩展登录、ERP 配置、维护表绑定和完整订单工程部署不包含在系统组件安装中。

## 首次配置

1. 启动发行包中的 EXE，进入“设置 → 连接与通知设置”。核对部门名称、工作区名称和数据目录。
2. 在库存来源中配置 SQL Server 地址、端口、数据库和查询账号，测试连接。选择记住密码时，由当前 Windows 用户加密保存在本机；换电脑不能仅复制加密文件代替登录。
3. 进入“管理监控商品”，按名称或 ERP 商品编号搜索添加，设置关注仓库、库存阈值及提醒类型。
4. 对照 ERP 核对一件商品同一仓库的实际可销、待审、实物库存和待入。首轮用于建立基线，不等于已验证通知投递。
5. 按需要添加通知机器人，核对群、机器人和通知类型，再启用相应规则。

SQL 必需对象：

| 对象 | 字段 |
| --- | --- |
| `[库存].[库存查询]` | `goods_id`、`商品编码`、`商品名称`、`总数量`、`可销数`、`待入` |
| `[库存].[分库库存]` | `goods_id`、`库房`、`商品编码`、`商品名称`、`分库数`、`分库可销数`、`分库待入`、`分库待审` |
| 成本功能额外读取 | `[库存].[分库库存]` 的 `库存成本` |

实际可销按同一库房的 `分库可销数 − 分库待审` 计算，保留负数。已有记录的待审 NULL 按零处理；必要字段缺失或没有该库房记录时保留未知，不代填零。分库待入与 ERP 总待入分别展示，总待入不能证明所选仓库已到货。

脚本来源是可选替代路径，需要浏览器采集脚本及相关环境；SQL 模式不需要启用浏览器采集或自动重登。详细规则见 [库存规则](inventory-setup.md)。

## 抖店库存巡检

添加本部门店铺并绑定主机维护表，连接各店专属浏览器后先核对实际登录的店铺。勾选“参与巡检”的店铺，进行一次手动检查，确认官方导出成功、SKU 与维护表匹配，再开启定时监控。

暂停定时巡检不禁止手动检查；手动检查仍可能产生符合规则的通知。正在执行的步骤需要结束后才能完成暂停。后台导出表示采集时刻的库存，前台是否可购买需要另外核实。

补库存提醒依赖新条目及真实库存核对；查看处理记录时区分本地结果、排队、发送成功和失败，不把排队当作通知已收到。

## 订单匹配与其他模块

在“订单机器人设置”指定完整匹配工程、控制目录、独立队列目录及运行程序，配置允许店铺。兼容后端部署前先停止旧服务，并处理在途或状态未知任务。保存配置不会自动启动匹配。具体步骤见 [订单后端说明](../integrations/order_backend/README.md)。

日常未匹配巡检查询昨天零点至本次开始时的待处理、未匹配订单，跳过已有有效关联。配置变化需使用明确的重新匹配入口。ERP 写入后必须回读；结果未知先查证，不直接重复提交。

在「设置 → 监控与巡检计划」集中查看和调整配件库存、抖店分店巡检、订单自动巡检、发货监控、ERP 调价、货源日报和缓存清理。各项独立保存，时间统一为北京时间。

发货监控卡片显示提醒群和周期。订单执行器运行时可「立即巡检」；也可独立启用或暂停定时监控。在「订单匹配 → 任务记录」查看执行和投递状态。群内「前台库存监控 店铺名」回复会向拥有表格链接权限且获准查看明细表全部店铺的成员附上对应链接。

价格变化、利润、货源日报周报及在线明细按需要配置；它们的来源和通知计划独立。缓存清理默认按所选范围处理，可预览后执行；配置、数据库和未完成记录不属于普通缓存。

## 更新与恢复

在侧栏点击“软件更新”，点击“检查更新”。开启“启动时自动检查更新”仅自动查询，不会静默安装。检测到新版本后查看说明，点击“一键更新并重启”。

程序先验证更新清单签名，再下载并核对文件大小及 SHA-256。校验失败时不替换原程序。安装前等待业务安全停止，存在执行中或待核验任务时需先处理；安装助手等待原进程退出后替换当前 EXE，再检查新版启动回执。

升级保留当前数据目录和人工记录，不因新版本重建店铺或重置暂停状态。原文件名可能保留，实际版本请看页面上的版本号。

原 EXE 旁保留 `.rollback-*` 恢复文件。新版启动失败且进程已退出时，助手尝试恢复旧 EXE；新版仍存活但未给出健康回执时不会强行终止业务，也不能宣称已自动回滚。此时查看工作区 `updates/install.json.result`，先正常退出并核对进程状态，再处理恢复文件。不要在仍运行时覆盖程序或删除工作区。

源码运行不通过更新器替换 Python，应按 [开发流程](开发与构建.md) 拉取和验证源码。更新包不会部署外部匹配工程或迁移其他电脑的登录状态。

## 数据与常见问题

新安装默认使用 `%LOCALAPPDATA%/BackendInventoryMonitor/workspaces/<安装目录摘要>`。旧安装旁存在 `.local_inventory_ui_test/inventory.sqlite3` 时继续使用原数据；显式 `--data-dir` 优先。完整数据规则见 [结构与数据流](结构与数据流.md#数据位置与更新边界)。

| 现象 | 处理 |
| --- | --- |
| 桌面无法显示或提示缺少 WebView2 | 重新运行一键环境检测，检查 WebView2 安装结果 |
| SQL 在线但某仓库数量未知 | 核对该商品同库房记录和字段权限，不用总库存代替 |
| 换目录后看不到原配置 | 核对工作区路径，使用明确的 `--data-dir`，不要继续建立第二套数据 |
| 检查更新失败 | 检查网络、发行通道及签名清单；失败不会修改现用 EXE |
| 更新提示业务未结束 | 查看订单、巡检及消息任务，等待实际停止后重试 |
| 机器人未收到消息 | 检查规则、机器人启用状态、目标及实际投递记录 |
| 一键部署失败 | 保留具体组件和错误信息，解决网络或安装权限后重试检测 |

同机多个独立工作区仍受当前固定业务端口约束，不能据此同时启动多个实例。跨电脑迁移需另外迁移配置、数据及登录，不应让多台电脑同时打开同一共享目录中的 SQLite 数据库。
