# 运营机器人指令接口规划

状态：待审阅。基线为 Gitea main `7c56886`。本文定义拟新增的接口及验收条件。

群成员实际 @ 运营机器人后，由它的现有接收程序识别指令、校验成员权限，调用库存监控的本机指令接口，再把结构化结果回复到发起群。库存监控负责商品解析、配置写入及任务回执，订单匹配仍由现有队列处理。联调前先确认运营机器人的应用身份、当前接收程序和运行主机，复用同一接收连接。

## 1. 指令和分期

下表省略群消息开头的 `@运营机器人`。帮助根据该群、成员和工作区已启用的权限生成。

| 群指令示例 | API 指令 | 参数与结果 | 阶段 |
| --- | --- | --- | --- |
| `帮助` | `help` | 返回当前可用指令、参数示例和命令权限 | 第一阶段 |
| `查库存 56281` / `查库存 5060 Ti 白色` | `inventory.get` | `goods_id` 或 `keyword` 二选一，`warehouse_id`、`shop_id` 可选。固定脚本优先，AI 辅助识别未解析的关键词。逐项返回商品名称、ERP ID、库存、ERP 价格和主机维护表价格 | 第一阶段 |
| `查价格变化 56281` | `price.changes` | `goods_id` 可选。查最近一个完成的检测批次，最多返回 10 条，附总数、批次时间、成本前后值和差额 | 第一阶段 |
| `添加监控 56281 阈值 5` | `monitor.add` | `goods_id`、`threshold` 必填，`stock_basis` 可选，指定分库时须有 `warehouse_id`。返回保存后的配置 | 第一阶段 |
| `匹配订单 店铺A 123456789012345A-1` | `order.match` | `shop_id`、`order_number` 必填。返回回执编号、后端任务号和入队状态 | 第二阶段 |
| `巡检订单 店铺A` | `order.patrol` | `shop_id` 必填。复用手动未匹配巡检任务 | 第二阶段 |
| `查看任务进度 <回执编号>` | `GET /api/commands/v1/requests/{request_id}` | 按群里收到的回执编号查询业务状态、执行摘要和群回复状态 | 第二阶段 |
| `查订单状态 123456789012345A-1` | `order.status.get` | `number` 必填，`number_type` 默认 `web_order_no`，`shop_id` 可选。默认按网店单号查，另支持 ERP NO、出库单号、物流单号 | 第二阶段 |
| `发货监控汇总` / `发货监控汇总 店铺A` | `shipping.summary` | `shop_id` 可选。读取钉钉 AI 表格中指定范围已回读核实的发货监控汇总 | 第二阶段 |
| `前台库存监控 店铺A` | `front_stock.summary` | `shop_id` 必填，`spu`、`sku_id` 可选。读取钉钉 AI 表格的前台库存监控明细，显示平台库存、配件核对和待处理状态 | 第二阶段 |

输入使用明确的命令和参数。接收端先验证真实 @ 事件及目标机器人身份，再处理首尾空格和参数之间的空白。商品 ID、SKU、店铺 ID、订单号均为字符串。群里可输入店铺别名，服务器按该工作区配置唯一解析。别名重名、写操作对象不唯一或参数缺失时提示补充。关键词查库存允许列出多项匹配。网店单号保留 `A`、`A-1` 等后缀。批量添加、移除监控、SPU 匹配和重新匹配待单独评审。

### 库存和监控口径

- 固定脚本优先。纯数字入参按完整 ERP 商品 ID 精确查询。输入名称、型号或 SKU 时查当前工作区 ERP 商品目录，统一大小写、全半角及型号空格，使用已确认的别名规则，多个明确条件须同时命中。完整名称或 SKU 的精确匹配优先，其余按商品名称、ERP ID 稳定排序。脚本已查到符合条件的多个商品时直接列出。按 ERP ID 去重，群回复最多列 5 件并标明总数，可加关键词或用完整 ID 缩小范围。目录有记录但没有库存快照时仍显示商品。
- 查询优先返回指定工作区最近一次已采集快照。库存值附仓库、采集时间和数据状态。公司大库可销按现有实际可销口径，所用数据支持待审扣减时一并返回 ERP 可销和待审。分库查询按该库实际数据返回。缺少指定库记录或快照时标为未知，真实零库存返回 `0`。
- ERP 价格首版明确为公司大库的配件库存成本单价，按已确认的 ERP 商品 ID 对本次展示项作批量只读查询。成本查询范围固定为公司大库，指定其他仓库查库存时仍单独标注成本来源。返回金额及读取时间，当前值不可用时显示“未知”。
- 主机维护表价格从已绑定、已保存的工作表读取。按 ERP 商品 ID 核对对应配件行或配置中的配件位置。表里有明确配件单价时展示“维护表配件单价”，附店铺和配置。只有整机到手价时，按店铺＋SPU＋SKU 关联到包含该配件的配置，展示“维护表整机到手价”。保留不同配置的不同价格，每个商品最多展示 3 条维护表价格并附总数，可通过 `shop_id` 缩小维护表范围。联调须核实实际价格列和读值方式，当前维护表清单读取器只解析配件关系，价格字段留空。表未绑定、未找到关联、价格列缺失和读取失败均单独标明。
- 两类价格按现有群、成员及店铺权限分别投影。查库存使用 `data.items` 返回 `name`、`goods_id`、`sku`、库存及 `erp_unit_cost_cents`、`erp_cost_observed_at`、`maintenance_prices`。维护表价格项带 `shop_id`、`spu`、`sku_id`、`config_name`、`price_kind`（`part_unit_price` 或 `host_checkout_price`）及 `price_cents`。同一来源的身份或价格存在冲突时标为待核实。金额用整数分，未知为 `null`。价格来源读取失败时保留已确认的商品及库存，在回执标记该来源状态。

### AI 辅助识别关键词

1. 固定脚本先解析「查库存」并查目录。ERP ID 或完整 SKU 精确匹配、固定规则已查到可靠结果时直接返回。明确输入的 ID 查不到时提示核对编号。只有口语、简称、疑似错别字等关键词未解析，或脚本未找到可靠匹配时，才在启用 AI 的工作区发起一次辅助识别。
2. AI 输入限于本次商品关键词。输出固定 JSON，提供最多三组候选搜索词和从原话提取的明确条件，例如型号、显存、品牌或颜色。比如“白色的五零六零钛，16G”可提取“5060 Ti、白色、16G”。显式条件随查询传回，校验格式和取值后由固定脚本重查目录。库存、ERP ID、价格和配置均由已核对的数据源取得。
3. 保留原话明确给出的规格，尤其是 `Ti`、`SUPER`、显存容量和颜色。脚本能核对全部条件时列出符合条件的真实商品。条件尚不能核对或可能对应不同型号时，返回 `outcome: needs_clarification`，列出可核对的候选名称和 ERP ID，请成员补充条件或按 ID 查询。
4. AI 关闭、超时、输出不合规或复查无结果时，返回脚本已核实的结果或提示补充型号、SKU、ERP ID。响应可用 `data.search_mode` 标识 `exact_id`、`keyword` 或 `ai_assisted`，经复查确认的检索条件放在 `data.interpreted_terms`。AI 辅助限于库存搜索条件，不扩展到命令路由或写操作。
- 首版添加监控要求明确阈值，范围沿用现有业务校验，为 0 至 100,000,000 的整数。默认口径拟沿用现有添加流程的公司大库实际可销（`company_able`）。成员指定分库时使用实物库存口径（`warehouse_stock`），须能唯一核对仓库 ID 和对应口径才允许保存。商品类别优先用已核实的类别，缺少时拟使用“其他”。提醒项沿用现有关注配置默认值，接收端回显实际生效项。
- 新增前用 ERP 商品 ID 从目录解析唯一商品和 SKU。新增、查重与记录请求结果在同一事务内处理。已关注时回读现有配置并返回 `already_exists`，包括成员提供的阈值和现有阈值不同时。已有关注的编辑使用现有管理入口。保存后回读确认，库存数值要等后续采集才可用。

### 订单状态查询

- 省略单号类型时，按完整网店单号（`web_order_no`）查。固定脚本在授权店铺内用 ERP 网店单号字段精确核对，保留 `A`、`A-1` 等后缀，先取得对应的 ERP `NO-` 单号再查状态。指定店铺可缩小范围。跨店命中或拆单关系无法唯一核实时，提示指定店铺或补全单号。查无记录时按已核实的查询范围提示，不推断订单不存在。
- 群命令也支持 `查订单状态 NO-示例`、`查订单状态 CK-示例`、`查订单状态 物流 SF示例`。固定脚本识别 `NO-`、`CK-` 前缀和明确的“物流”参数，分别传 `erp_no`、`outbound_no`、`tracking_no`，映射到 tiny_tools 的 `NO单号`、`出库单号`、`物流单号`。每次传一个完整字符串，保留前导零，类型和单号冲突时提示更正。
- 由 Python 3.14 的订单后端接入 [tiny_tools PR #5](https://gitea.cq360.top/CoreStudio/tiny_tools/pulls/5) 的已合并实现。匹配项目当前固定的源码提交早于此功能，联调需核对依赖提交和实际运行环境，验证匹配及发货巡检回归。库存监控通过后端接口调用。
- 按完整单号查关联订单并核对店铺授权。一个 CK 或物流号可能关联多张 NO 订单，返回合并时间线前须逐张确认权限。关联范围无法核实或包含未授权店铺时，整次查询拒绝。群回复注明关联订单数量，默认显示步骤、时间和对应单号，操作人字段按试点群权限配置展示。
- 回复先展示最近业务记录，再展示实际发生的步骤，例如财审、装机、系统测试、打包、出库或退货入库。最近记录只取时间可核实的最新事件；同一时间有多条则一并展示。有记录但全部时间未知时，回复“最近状态待核实”并列出已有记录。关联多张订单时标为“关联订单最近记录”，避免把其中一张的进度套给其他订单。
- `data.events` 按实际发生时间升序排列，每条包含 `step`、`operator`、`occurred_at`、`reference_number`，空值用 `null`。保留重复发生的步骤，时间无法解析的记录排末尾。另返回 `data.latest_events` 和 `data.order_count`，分别表示时间可核实的最新记录和已确认的关联订单数量。找到订单但无符合条件的记录时返回 200、`outcome: no_records`；单号查不到返回 404；ERP 或登记表读取失败返回 `503 SOURCE_UNAVAILABLE`。按回执查匹配任务仍使用“查看任务进度”。

### 钉钉 AI 表格接入

- 发货监控汇总和前台库存监控使用钉钉 AI 表格作为群查询来源。原监控任务负责采集、同步和回读，运营机器人按固定脚本读取已绑定的表。群指令只读取已有结果，查看汇总时无需重新运行巡检。回复显示所用批次或快照时间，按权限附同一批次实际使用的表格链接。
- 通过 `dws aitable` 在同一组织 profile 中按 Base、表和字段的稳定 ID 读取。绑定前核对真实表与字段类型，查询时按店铺和批次筛选并检查分页完整性。表格未绑定、权限不足、读取失败、同步结果未知和没有业务记录分别返回；分页不完整时只报告已核实范围。
- 保存或关联可验证的批次标识、检查时间、覆盖店铺及同步结果。只有回读确认的数据可作为已同步结果展示。若新一轮同步未确认，已有已验证批次可带原时间展示并提示本轮状态。后台同步按业务键对齐，只更新程序负责的字段，保留人工处理状态和备注。不同批次的明细和统计分别标明时间。

### 发货监控汇总

- 复用现有发货订单表与缺货配件表。查询取对应店铺范围内已回读的批次汇总；两张表现有明细不足以推导该轮完整扫描量和覆盖范围时，由原监控任务补同步批次汇总。无店铺参数时使用该群和成员获授权的默认范围。指定店铺时按稳定店铺 ID 读取有明确来源的单店统计，范围或口径无法确认时提示暂无该范围汇总。
- 待发扫描沿用现有发货监控口径，覆盖历史未完成的待客审、待打印、已打印订单。紧急分为距离承诺发货截止不超过 48 小时和已超时两类，截止时间未知单列。缺货汇总覆盖该轮全部待发需求，沿用后端按公司大库现货、可销和订单状态核算的缺口，不把待入当现货，也不重复扣减已占用需求。缺货配件按 ERP 商品 ID 去重，数量和缺口按件展示。
- 回执 `data` 包含 `report_id`、`checked_at`、`shop_ids`、`coverage`、`counts`、`shortage_items` 和两张表各自的批次、时间、同步状态及授权链接。非同批数据分别归到对应表的汇总项。其中 `counts` 包含 `pending_scanned`、`overdue`、`due_within_48h`、`deadline_unknown`、`shortage_goods` 和 `inventory_unknown_goods`。覆盖不完整时标明影响范围，已核实的数字明确为已查范围，无法确定的数字返回 `null`。无报告返回 `outcome: no_report`。
- 分别展示发货订单表和缺货配件表的原同步回执。一张表读取或同步异常时，另一张表可独立展示已核实结果，并标明各自时间。只有同一批次且范围一致的数据才合并展示。

### 前台库存监控

- 复用现有前台库存补库存明细表，按店铺＋SPU＋SKU 对齐。群内展示商品和配置名称、平台库存、配件检查、补库存标记、人工处理状态、平台快照时间及配件核对时间。按权限提供现有明细表入口。已退出提醒的行从当前待处理汇总排除；SKU 未匹配、配件待核对和平台库存未知各自显示。
- 现有表覆盖补库存、低库存和待核对记录，群回复标明“在线监控明细”范围。按 SPU 或 SKU 查不到行时回复“暂无在线监控记录”，无法由此判断该 SKU 实时库存。如果后续要查询全量前台库存，原监控任务需要把全量采集快照同步到独立表并记录完整性。
- `data` 返回 `snapshot_id`、`shop_id`、`coverage`、`counts`、`items` 和授权后的 `table_url`。统计使用同店、同一批次且权限可见的业务键。全量匹配数与本次展示数分开，群回复最多列 5 条明细。

## 2. 接口契约

首选由同机运营机器人适配器调用库存监控的回环地址，复用现有应用服务及工作区。若核实接收端运行在其他主机，再评审经认证的中转和连通性。调用方身份使用单独的指令凭证，服务端按凭证绑定工作区和指令权限，按钉钉组织、群、成员的稳定标识授权。群成员标识只由可信接收程序从已验证的钉钉事件填入。请求体内的显示名或群文本不参与授权。

| HTTP | 用途 |
| --- | --- |
| `GET /api/commands/v1/capabilities` | 返回版本、指令参数定义及可授权能力，供接收端检查兼容性 |
| `POST /api/commands/v1/requests` | 校验并执行一个指令。同步结果返回 200，成功入队返回 202 |
| `GET /api/commands/v1/requests/{request_id}` | 读取指定请求的执行结果和投递状态，重新校验群、成员及工作区范围 |

请求体示例。示例标识和数据均为占位。

```json
{
  "request_id": "dingtalk:evt-demo-001",
  "command": "monitor.add",
  "actor": {
    "org_id": "org-demo",
    "group_id": "group-demo",
    "user_id": "member-demo"
  },
  "args": {
    "goods_id": "56281",
    "threshold": 5,
    "stock_basis": "company_able"
  }
}
```

`request_id` 由接收端根据钉钉组织和稳定消息标识生成，同一事件的多次投递使用相同 ID。接收端凭证通过 `Authorization` 请求头传递。读取请求时，由受信接收端用 `X-Actor-Org-Id`、`X-Actor-Group-Id`、`X-Actor-User-Id` 传入本次查询成员的身份。首版任务详情只对同群原发起人开放。回执字段固定为 `request_id`、`command`、`status`、`code`、`message`、`data`，异步任务另有 `task_id`。群里显示的回执编号为 `request_id`。机器按状态和代码处理，群回复用业务数据生成。

```json
{
  "request_id": "dingtalk:evt-demo-001",
  "command": "monitor.add",
  "status": "completed",
  "code": "OK",
  "message": "已添加监控，配置已回读",
  "data": {
    "outcome": "created",
    "goods_id": "56281",
    "sku": "DEMO-SKU",
    "warehouse_name": "公司大库",
    "stock_basis": "company_able",
    "threshold": 5
  }
}
```

| HTTP 或状态 | 约定 |
| --- | --- |
| `400 INVALID_ARGUMENT` | 字段、类型或指令不合法。指出需要补充或更正的参数 |
| `403 FORBIDDEN` | 凭证、群、成员、店铺或指令越权。跨范围请求不泄露对象详情 |
| `404 NOT_FOUND` | 授权范围内无此商品或任务 |
| `409 AMBIGUOUS_TARGET` / `IDEMPOTENCY_CONFLICT` | 目标存在多个匹配，或同一请求 ID 对应不同参数。需要明确目标或检查接收端 |
| `503 SERVICE_UNAVAILABLE` | 执行前确认库存服务或订单工作进程不可用。返回具体缺失环节 |
| `503 SOURCE_UNAVAILABLE` | 订单状态查询的 ERP 或登记表读取失败，或发货报告数据源读取失败 |
| `queued → running → completed / needs_review / failed / unknown` | 已入队、执行中、完成、需人工核对、已确认失败、执行结果未知。部分匹配使用 `needs_review` 并返回成功、跳过和待核对数 |
| `delivery_status` | 分别记录回复待发、已投递、失败或未知。投递结果与业务结果独立 |

### 重复投递和订单边界

- 用工作区、接收来源及请求 ID 建立持久唯一约束，记录指令、参数摘要、发起者、执行状态和后端任务号。同一消息重新到达时回读原请求，进程重启后仍有效。未知结果先按原请求查证，避免重复写入。
- 订单沿用现有匹配和回读流程。普通匹配跳过已有有效关联，人工巡检沿用现有未匹配筛选。新接口入队前核对店铺、工作进程心跳及启停状态，不隐式启动已停用服务。自动巡检暂停和手动指令是两个状态。
- 后端需在订单入队同一事务持久记录外部请求 ID 与任务 ID 的对应关系。现有短时间去重可保留用于同一业务对象的在途保护。跨服务调用超时后用外部请求 ID 回读队列；未确认时保留 `unknown`，等待人工核对。
- 运营机器人负责其指令的入队回执和最终群回复。第二阶段联调时用任务来源区分运营机器人指令和已有定时通知，确保一个指令任务只有一个最终群回复发送方。群回复投递未知时先查证回执。

## 3. 群回复文案

按 [运营机器人群回复文案规范](运营机器人群回复文案规范.md) 渲染群消息。模板由指令、业务状态和错误代码决定，验收时核对接口回执、文案与实际投递。

## 4. 实施和验收

1. 对接前确认运营机器人当前接收程序、运行位置，以及试点群和允许操作的人员。第一阶段先启用帮助、库存和价格查询，再试点添加监控。试点阈值和监控范围由发起人明确提供。
2. 对库存侧实现版本化命令路由和最小权限。查询复用 [现有数据接口](机器人数据查询接口.md)，保存复用现有关注逻辑并补齐原子查重与写后读。用隔离数据覆盖 ERP ID 和脚本直查时不调用 AI、口语型号提取、型号或显存不符、AI 超时回退、关键词多商品、同名不同 ID、真实零库存、缺失仓库、同配件跨店不同维护表价、价格列缺失及价格越权。新增监控覆盖重复事件、并发新增和进程重启。
3. 订单侧基于 [现有兼容层](../integrations/order_backend/README.md) 对接外部请求 ID、任务查询和回复归属。用隔离队列验证已停用、排队、部分成功、未知写入及投递不重复。库存接口与订单工作进程分别回读。
4. 订单状态查询验收覆盖默认网店单号关联 NO、完整后缀、跨店或拆单歧义、四种单号查同一订单返回一致结果、最近记录取值、时间未知、多订单关联、跨店越权、重复步骤、无记录和登记读取失败。发货汇总和前台库存监控验收覆盖钉钉 AI 表格绑定、跨店权限、分页完整性、写后回读、批次不一致、缺失记录、部分同步和未知状态。验证群查询使用固定脚本只读表格，现有同步流程保留人工字段。
5. 试点群实测真实 @、允许的查询、拒绝越权和回复归属。通过后再逐项启用写指令。版本和开放指令范围随功能 PR 记录。
